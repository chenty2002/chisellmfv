# Counterexample Analysis Report: `prediction_stable_during_stall`

## 1. Verification Environment

- **Top Module**: `branchPredictionBuffer` (class in `bpbs.scala`)
- **Generated Verilog**: `generated/branchPredictionBuffer.sv`
- **Key Components**:
  - **4 state banks** (`state_bank0`–`state_bank3`): Each bank contains 4 entries of 2-bit saturating counters (initialized to weak-not-taken `01`).
  - **`prediction` register**: 4-bit register updated on non-stalled cycles by reading the MSB of each bank's entry at `io.inst_addr`.
  - **Update logic**: When `io.update` is asserted, one bank (selected by `io.buffer_offset`) is incremented (taken branch) or decremented (not-taken branch) at address `io.buffer_addr`.
  - **`r` register**: A 1-cycle delayed copy of `prediction` (generated by the ChiselFv `assertStableWhen` helper).

## 4. Root Cause Analysis

### Root Cause Category: **Assertion Error**

The assertion is incorrectly constructed for this design's timing characteristics. It is NOT a bug in the DUT — the design correctly updates `prediction` only on non-stalled cycles.

### Detailed Trace

The failure is a **1-cycle timing mismatch** between `prediction` and its delayed copy `r`.

#### Cycle 1 (posedge at t=0 ns):
- `io_stall = 0`, `io_update = 1`, `io_branch_result = 1` (taken), `io_buffer_offset = 3`, `io_buffer_addr = 0`
- The taken-branch update targets `state_bank3(0)`. Since `state_bank3_0 = 01` (not saturated at max 3), it increments: **`state_bank3_0 <= 01 + 1 = 10`** (NB assignment)
- Since `!stall`, prediction is recomputed: all four bank MSBs at `io_inst_addr = 0` are `0` (all banks = `01`), so **`prediction <= 0000`** (NB — same as current value)
- **`r <= prediction = 0000`** (NB — captures pre-update prediction value)

#### Cycle 2 (posedge at t=10 ns):
- `io_stall = 0`, `io_update = 1`, `io_branch_result = 0` (not taken), `io_buffer_offset = 1`, `io_buffer_addr = 0`
- NB updates from cycle 1 have taken effect: `state_bank3_0 = 10`
- The not-taken update targets `state_bank1(0)`. Since `state_bank1_0 = 01` (not at min 0), it decrements: **`state_bank1_0 <= 01 - 1 = 00`** (NB)
- Since `!stall`, prediction is recomputed: `state_bank3_0` MSB = 1, others = 0 → **`prediction <= 1000`** (NB)
- **`r <= prediction = 0000`** (NB — captures the OLD prediction value 0000 before the NB update)

#### Cycle 3 (posedge at t=20 ns) — **FAILURE**:
- `io_stall = 1`, `io_update = 1`, `io_branch_result = 0`
- NB updates from cycle 2 have taken effect: `state_bank1_0 = 00`, `prediction = 1000`, `r = 0000`
- Since `io_stall = 1`, prediction is **NOT** updated (remains 1000)
- **Assertion check**: `~io_stall | prediction == r` = `~1 | (1000 == 0000)` = `0 | 0` = **0 → FAIL**

### Why This Is an Assertion Error

In Verilog, non-blocking assignments ( `<=` ) take effect at the **end** of the time step. On the same posedge, all right-hand sides are evaluated using the **pre-update** values. This means:

1. At t=10, `r <= prediction` captures `prediction`'s **old** value (0000), not the newly computed value (1000).
2. At t=20, when `io_stall` first goes high, `prediction` presents the **new** value (1000) computed at t=10, but `r` still holds the **old** value (0000) from t=10.
3. The assertion expects `prediction == r` during stall, but `r` is always exactly **one cycle behind** the NB-updated `prediction`.

The design behavior is actually **correct**: the prediction register is only updated when `!io_stall`, and the stall signal correctly suppresses updates. The "change" that the assertion detects is actually the NB update from the previous non-stalled cycle propagating — not an unexpected change during stall.

### The Buggy Code

**File**: `bpbs.scala`, **Line 88**:
```scala
assertStableWhen(io.stall, prediction, "prediction_stable_during_stall")
```

The `assertStableWhen` helper (from ChiselFv) creates a 1-cycle delayed copy `r` of `prediction` and checks `~io.stall | prediction === r`. This formulation is too strict for a register that is updated via non-blocking assignment on non-stalled cycles — it creates a false-positive failure on the first stalled cycle after any non-stalled update.

### Suggested Fix

The assertion should account for the 1-cycle pipeline delay. Possible fixes:

1. **Use a 2-cycle delayed copy**: Compare `prediction` with a version delayed by 2 cycles instead of 1:
   ```scala
   val r2 = RegNext(r, 0.U)
   fvAssert(!io.stall || prediction === r2, "prediction_stable_during_stall")
   ```

2. **Check stability across consecutive stalled cycles**: Only assert stability when stall has been asserted for at least 2 consecutive cycles:
   ```scala
   val stall_delayed = RegNext(io.stall, false.B)
   fvAssert(!(io.stall && stall_delayed) || prediction === r, "prediction_stable_during_stall")
   ```

3. **Direct formal check without delayed copy**: Use `stable()` from ChiselFv if available, or use past operators to check that `prediction` is not modified while stalled (the design already doesn't update it).
