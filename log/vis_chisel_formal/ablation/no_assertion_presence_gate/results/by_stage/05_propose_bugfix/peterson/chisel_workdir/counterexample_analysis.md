# Peterson Liveness Counterexample Analysis Report

## 1. Verification Environment

### Top Module
`peterson` — a Chisel implementation of Peterson's mutual exclusion algorithm with formal verification assertions.

### Top Module Structure
```
peterson
├── io.select       (Input Bool)  — Scheduler selects which process to run (0→process 0, 1→process 1)
├── io.pause        (Input Bool)  — Pause signal to stall process execution
├── io.interested   (Output Vec(2, Bool)) — Interest flags for each process
├── io.turn         (Output Bool) — Turn variable for tie-breaking
├── io.self         (Output Bool) — Currently selected process index
├── io.pc           (Output Vec(2, Loc)) — Program counters for each process
└── Internal Logic
    ├── pc(0), pc(1)        — Program counters (L0..L5)
    ├── interested(0/1)     — Interest registers
    ├── turn                — Turn register
    ├── self                — Self register (latches io.select)
    ├── timer [4:0]         — Liveness timer for process 0 (generated by astRelaxedLiveness)
    ├── timer_1 [4:0]       — Liveness timer for process 1
    ├── pending             — Liveness pending flag for process 0
    ├── pending_1           — Liveness pending flag for process 1
    └── resetCounter        — Reset stabilization counter
```

### Design Under Test
The DUT implements Peterson's algorithm as a single-threaded state machine that executes one process per cycle, selected by `io.select`. Each process has a 6-state program counter (L0–L5) implementing the algorithm's entry protocol, critical section, and exit protocol. The design is verified with:
- **Safety**: Mutual exclusion (both processes never simultaneously in L4)
- **State consistency**: Various implication assertions about pc ↔ interested
- **Bounded liveness**: Each process must enter the critical section (L4) within 15 cycles of arriving at the entry protocol (L3)

## 2. Violated Assertion

### Full Assertion Name
`liveness_p0_entry`

### Code Snippet
From `peterson.scala`, line 107:
```scala
astRelaxedLiveness(pc(0) === Loc.L3, pc(0) === Loc.L4, 15, "liveness_p0_entry")
```

### Property Description
When process 0's program counter reaches the entry protocol state L3 (waiting at the Peterson entry gate), it must eventually reach the critical section L4 within 15 clock cycles. This is a **bounded liveness** property: the process cannot be stuck waiting at L3 for more than 15 consecutive cycles.

### File Location
- **File**: `peterson.scala`
- **Line**: 107

## 4. Root Cause Analysis

### Error Classification: **Setup Issue** (Category 3)

The root cause is an **unconstrained `io_select` input** that the formal verification tool holds at 1 from cycle 3 onwards, creating a denial-of-service scenario where only process 1 is scheduled.

### Buggy Location
- **File**: `peterson.scala`
- **Lines**: 20 (io.select declaration), 42 (self := io.select)

### Description of the Bug

The `io_select` input (consumed via `io.select`) determines which process executes in each cycle:
```scala
val self = RegInit(0.U(1.W))
self := io.select
```

The `io_select` signal is an **unconstrained primary input** — the formal verification tool is free to assign any sequence of values to it. In this counterexample, the tool holds `io_select` at 1 from time 20 onwards (sampled starting at time 30's posedge), so only process 1 is scheduled for execution after cycle 3.

### Execution Trace and Deadlock Mechanism

**Phase 1 — Normal execution (cycles 0–2):**
- Cycle 0–2: `io_select=0`, process 0 executes and progresses through L0→L1→L2→L3
- At time 20, `io_select` transitions from 0 to 1

**Phase 2 — Stuck at L3 (cycles 3–19):**
- **Cycle 3** (time 30): `self` latches `io_select=1`. Process 0 has reached L3 but is now never scheduled again.
- **Cycle 3–5**: Process 1 executes: L0→L1→L2→L3 (setting `turn := ~1 = 0`)
- **Cycle 6+**: Both processes are at L3, but `self=1`, so only process 1 is evaluated

**Deadlock at L3 for both processes:**

For process 1 (being scheduled each cycle):
- L3 entry condition: `when(!interested(otherIdx) || (turn === self))`
- `otherIdx = ~1 = 0`
- `interested(0) = 1` (process 0 remains interested)
- `turn = 0` (set by process 1 in cycle 5)
- `turn === self → 0 === 1 → false`
- **Both subconditions fail** → process 1 is permanently stuck at L3

For process 0 (never scheduled):
- `self=1`, so `pc(selfIdx) = pc(1)`. Process 0's state machine is never evaluated.
- Process 0 is permanently stuck at L3.

**Phase 3 — Timer timeout:**
- The `astRelaxedLiveness` macro starts a timer when `pc(0)=L3` (pending goes high at time 40).
- Timer counts: 0→1→2→...→15 over 16 cycles (time 50 to time 190).
- At time 190, timer=15 and pc(0) is still L3 → **assertion violation.**

### Why This Is a Setup Issue, Not a DUT Bug

The Peterson algorithm implemented in the DUT is **correct as a mutual exclusion protocol** — the mutual_exclusion assertion passes, and all state consistency assertions pass. The problem is with the **verification environment**:

1. **`io_select` is unconstrained**: In the real hardware that Peterson's algorithm was designed for, both processes execute truly concurrently (separate state machines in parallel hardware). The Chisel model uses a single-threaded abstraction where `io_select` chooses which process runs each cycle. Without a fairness constraint on `io_select`, the formal tool can trivially hold one process's execution indefinitely.

2. **Liveness requires fairness**: The bounded liveness assertion `astRelaxedLiveness(pc(0) === L3, pc(0) === L4, 15, ...)` assumes that a scheduling opportunity exists within 15 cycles. But `io_select=1` means process 0 gets **zero** scheduling opportunities, making the bound impossible to satisfy.

3. **The deadlock at L3 is a consequence of single-threaded scheduling, not the algorithm**: In a truly concurrent implementation, process 0 would independently check `(!interested(1) || (turn === 0))`, find `turn = 0` and `turn === 0` true, and enter L4 regardless of process 1's state.

### Recommended Fix

To fix this verification setup issue, add a **fairness constraint** on `io_select` to ensure both processes are scheduled regularly. In Chisel FV, this can be done with an `astAlways` assertion that constrains `io_select` to toggle periodically:

```scala
// Constrain io_select to eventually select each process
astAlways(io_select =/= RegNext(io_select))  // or more complex fairness
```

Alternatively, add an invariant that tracks the number of consecutive cycles the same process is selected and limits it to a reasonable bound (e.g., 3-4 cycles, which would still allow Peterson's algorithm to make progress).
