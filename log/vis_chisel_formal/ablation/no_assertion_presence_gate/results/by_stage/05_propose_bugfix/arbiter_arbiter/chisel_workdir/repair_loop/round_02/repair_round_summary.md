Repair round 2/3 — handled failing property `ackImpliesReq` (error_type: dut_bug). Root cause: the Controller's BUSY-state transition waited for `!io.req` before releasing ackReg, but `io.req` is a register output from the Client module (reqReg). Under Verilog non-blocking-assignment semantics, both update on the same posedge, so the Controller samples the old req value (still 1) and misses the transition, keeping ack high after req has dropped. Fix: made the BUSY→IDLE transition unconditional (removed `when(!io.req)` guard) so that ack is asserted for exactly one cycle (READY→BUSY) and then released immediately without waiting for the client's req to drop. This preserves causal correctness: the ack pulse is a one-cycle grant that the client samples on the same posedge it transitions REQ→HAVE_TOKEN, before req drops in a subsequent cycle. The assertion label `ackImpliesReq` is preserved unchanged. No homologous assertions exist because this is a DUT bug affecting all three Controller instances identically; the single structural change in the BUSY case applies to all controllers.
