# Counterexample Analysis Report: passTokenMutex

## 1. Verification Environment

- **Top Module**: `Main` (from `arbiter.scala`)
- **Design Structure**: The system consists of:
  - Three `Client` modules (A, B, C) that generate random requests
  - Three `Controller` modules (A, B, C) that handle the handshake protocol and pass the token
  - One `Arbiter` module that cycles through controllers A→B→C→A when active
  - The `Main` module wires all components together
- **Design Under Test (DUT)**: The `Main` module, as generated by `VerilogGenerator`

## 2. Violated Assertion

- **Assertion Name**: `passTokenMutex`
- **Waveform Filename**: `Main.passTokenMutex.fst`
- **File Location**: `arbiter.scala`, lines 226-229

**Code Snippet**:
```scala
AssertProperty(
  !(io.passTokenA && io.passTokenB) &&
  !(io.passTokenA && io.passTokenC) &&
  !(io.passTokenB && io.passTokenC),
  None, None, Some("passTokenMutex")
)
```

**Description**: This safety property asserts that at most one controller may assert its `passToken` output at any time. The token-passing protocol requires exclusive ownership of the token — if two or more controllers simultaneously believe they hold the token, double-granting can occur, breaking the mutual exclusion invariant.

## 4. Root Cause Analysis

### Bug Classification: **Bug in the Original Design (DUT Bug)**

### Bug Location
**File**: `arbiter.scala`, line 72
**Module**: `Controller`
**Buggy Code**:
```scala
val passTokenReg = RegInit(true.B)
```

### Bug Description
All three Controller modules initialize their `passTokenReg` to `true.B`. This means every controller starts with its `passToken` output asserted at reset. The token-passing mutual exclusion invariant requires that **exactly one** controller holds the token at any time, but the design incorrectly grants the token to all three controllers simultaneously at power-on/reset.

Since all three passToken signals are 1 at time 0:
- `io.passTokenA && io.passTokenB` = 1 && 1 = 1 → `!(1)` = 0
- `io.passTokenA && io.passTokenC` = 1 && 1 = 1 → `!(1)` = 0
- `io.passTokenB && io.passTokenC` = 1 && 1 = 1 → `!(1)` = 0
- The conjunction `0 && 0 && 0` evaluates to **0** → **assertion violation**

### Evidence from Waveform
The waveform traces confirm that at time 0 (immediately after reset):
1. `Main.controllerA.passTokenReg` = **1** (never changes during simulation)
2. `Main.controllerB.passTokenReg` = **1** (never changes during simulation)
3. `Main.controllerC.passTokenReg` = **1** (never changes during simulation)
4. `Main.passTokenMutex` = **0** (failing from the very first cycle)

### Proposed Fix
Change the initialization so that **only one** controller starts with the token. For example:

```scala
// In Controller class — parameterize the initial token value
class Controller(id: Selection.Type, hasInitialToken: Boolean = false) extends Module {
  // ...
  val passTokenReg = RegInit(if (hasInitialToken) true.B else false.B)
  // ...
}

// In Main — only controllerA starts with the token
val controllerA = Module(new Controller(Selection.A, hasInitialToken = true))
val controllerB = Module(new Controller(Selection.B, hasInitialToken = false))
val controllerC = Module(new Controller(Selection.C, hasInitialToken = false))
```

Alternatively, use a one-hot initialization pattern where exactly one controller's `passTokenReg` is initialized to `true.B` and the others to `false.B`.
