# Counterexample Analysis Report

## 1. Verification Environment

- **Top Module**: `usb_phy` (package `llmverify`)
- **TestTop**: Generated by `chiselFv` formal verification framework
- **Key Components**:
  - `usb_phy` - Main USB PHY module with USB reset detection logic
  - `usb_tx_phy` - Placeholder TX PHY (always outputs 0)
  - `usb_rx_phy` - Placeholder RX PHY (always outputs LineState=0)
- **Design Description**: A USB PHY module that monitors the USB bus lines for SE0 state (both D+ and D- low) and asserts a USB reset signal when the SE0 state persists for 31 clock cycles while the system reset (`io.rst`) is active.

## 2. Violated Assertion

- **Assertion Name**: `usb_rst_eventually_asserted`
- **Source Location**: `usb_phy.scala`, lines 117-122
- **Code**:
  ```scala
  astRelaxedLiveness(
    io.rst && io.LineState_o === 0.U && !usb_rst_reg,
    usb_rst_reg,
    40,
    "usb_rst_eventually_asserted"
  )
  ```
- **Property Description**: This is a relaxed liveness property asserting that if at any cycle the system reset is active (`io.rst=1`), the USB line is in SE0 state (`io.LineState_o=0`), and the USB reset register has not yet been set (`usb_rst_reg=0`), then within the next 40 clock cycles the USB reset register (`usb_rst_reg`) should become asserted.

## 3. Waveform Information

- **Waveform File**: `verilog/extra_bench/usbphy/usb_phy.usb_rst_eventually_asserted.fst`
- **Duration**: 42 cycles (420 ns)
- **Waveform Time Range**: 0 ns → 420 ns (all times are in nanoseconds; cycle period = 10 ns)

### Key Timeline of Events

| Time (ns) | Event |
|-----------|-------|
| t=0 | `io.rst`=1, `io.LineState_o`=0, `usb_rst_reg`=0 → **Antecedent fires**, pending starts tracking |

| Signal | Value | Meaning |

## 4. Root Cause Analysis

### Category: **Setup Issue (TestTop constraint problem)**

### Root Cause: Missing constraint on `io.rst` stability in the formal verification environment

**The Problem:**

The counterexample shows that `io.rst` (the system reset input) toggles unpredictably during the formal verification run:

1. At t=0, `io.rst`=1 (active), starting the USB reset detection
2. At t=10, `io.rst` drops to 0, which causes `rst_cnt` to reset to 0 (line 74: `when(!io.rst) { rst_cnt := 0.U }`)
3. The counter only resumes counting from zero when `io.rst` goes high again at t=310
4. By t=410, `io.rst` drops again, with `rst_cnt` only reaching 10 — far short of the 31 required for USB reset detection

The `io.rst` signal toggles four times during the 420ns simulation, preventing the counter from ever accumulating 31 consecutive active cycles. This behavior is unrealistic for a system reset signal — `io.rst` should remain stable (high) for the entire duration needed for USB reset detection.

**Why this is not a DUT bug:**

- The counter logic (lines 74–80) correctly implements the USB reset detection algorithm: it counts only when `io.rst` is active (high), the line is in SE0 state, and USB reset hasn't been detected yet
- The counter properly resets when `io.rst` goes low, which is the expected behavior for a system reset
- The `usb_rst_reg` persistence logic and the `reset_wire` generation (`io.rst & ~usb_rst_reg`) are correct
- The TX and RX PHY placeholders output valid values (LineState=0, which is the SE0 condition)

**Why this is not an assertion error:**

- The `astRelaxedLiveness` property is correctly formulated: it checks that if the system reset and SE0 conditions hold, USB reset should assert within 40 cycles
- The 40-cycle bound is reasonable (above the 31 cycles needed by the counter)
- The antecedent condition (`io.rst && io.LineState_o === 0.U && !usb_rst_reg`) accurately captures the trigger condition for USB reset detection

**The Fix:**

The TestTop module (formal verification harness) needs to add a constraint that `io.rst` remains stable (high) once asserted, at least until the USB reset is detected. Specifically:

- `io.rst` should be constrained to stay high for at least 31 consecutive cycles when the assertion condition is active
- Alternatively, `io.rst` could be treated as a non-deterministic but stable signal (e.g., constrained to toggle only under specific conditions)

### Buggy Location

The issue is **not in the DUT source code** (`usb_phy.scala`), but rather in the missing formal constraints in the **TestTop module** (the generated formal verification harness). The formal environment should include a constraint such as:

```scala
// io.rst should remain high once asserted, for the duration of USB reset detection
fvAssume(stable(io.rst, 31) || usb_rst_reg, "rst_stable_during_usb_reset_detection")
```

or equivalently in Verilog:

```verilog
// assume that io_rst stays high once it goes high
always @(posedge clock) begin
    if ($rose(io_rst) && !usb_rst_reg)
        ##0 assume(io_rst throughout ##[0:30] 1);
end
```

This constraint prevents the unrealistic toggling behavior of `io.rst` and allows the USB reset detection counter to reach its terminal value of 31.
