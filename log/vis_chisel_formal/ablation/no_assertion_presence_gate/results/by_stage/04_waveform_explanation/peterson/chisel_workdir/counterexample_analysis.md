# Counterexample Analysis Report: peterson.liveness_p0_entry

## 1. Verification Environment

- **Top Module**: `peterson` (in package `llmverify`)
- **Source File**: `peterson.scala` (113 lines)
- **Design Under Test**: Peterson's mutual exclusion algorithm with two processes (index 0 and 1) using shared variables (`interested[2]`, `turn`). The design uses a time-multiplexed execution model where only one process advances per clock cycle, selected by the `self` register (which captures the value of `io_select`).
- **Key Components**:
  - `pc(0), pc(1)`: Program counters (L0–L5 enum)
  - `interested(0), interested(1)`: Interest flags
  - `turn`: Turn variable for tie-breaking
  - `self`: Selects which process executes (`selfIdx = self`, `otherIdx = ~self`)
  - `timer` / `pending`: Liveness checking infrastructure generated by `astRelaxedLiveness`

## 2. Violated Assertion

- **Assertion Name**: `liveness_p0_entry`
- **Full Path**: `peterson.liveness_p0_entry`
- **Waveform File**: `peterson.liveness_p0_entry.fst`

### Code Snippet

```scala
// Line ~95 in peterson.scala
astRelaxedLiveness(pc(0) === Loc.L3, pc(0) === Loc.L4, 15, "liveness_p0_entry")
```

### Natural Language Description

When process 0 reaches the entry protocol (L3 — the waiting/looping state), it must eventually reach the critical section (L4) within 15 clock cycles. Peterson's algorithm guarantees starvation-freedom: if a process is waiting at L3, it should enter the critical section after at most one pass of the other process through the critical section.

- **File**: `peterson.scala`, line ~95
- **Module**: `class peterson extends Module with Formal`

## 4. Root Cause Analysis

### Root Cause Category: **setup_error** (Missing Fairness Constraints)

### Buggy Code Location

**File**: `peterson.scala`, lines 38-84 (the state machine logic) and lines 85-113 (formal verification section).

**The state machine** (lines 38-84):

```scala
val selfIdx = self
val otherIdx = ~self

switch(pc(selfIdx)) {
  is(Loc.L0) { when(!io.pause) { pc(selfIdx) := Loc.L1 } }
  is(Loc.L1) { interested(selfIdx) := true.B; pc(selfIdx) := Loc.L2 }
  is(Loc.L2) { turn := ~self; pc(selfIdx) := Loc.L3 }
  is(Loc.L3) { when(!interested(otherIdx) || (turn === self)) { pc(selfIdx) := Loc.L4 } }
  is(Loc.L4) { when(!io.pause) { pc(selfIdx) := Loc.L5 } }
  is(Loc.L5) { interested(selfIdx) := false.B; pc(selfIdx) := Loc.L0 }
}
```

### Description of the Bug

The design uses a **time-multiplexed execution model**: only ONE process advances per clock cycle, selected by the `self` register (which samples `io_select` each cycle). Both processes progress through the same state machine, but the machine only advances the PC of the selected process (`selfIdx`).

The `io_select` input is **completely unconstrained** — there are no assumptions (`assume`) or fairness constraints that require it to alternate.

In the counterexample waveform:

1. **Process 0 reaches L3** at cycle 3 (time=30) and sets `turn = 1`.
2. **`io_select` transitions to 1 at cycle 6** (time=60) and **stays at 1 for all remaining cycles**.
3. **Both processes are at L3** from cycle 7 onward (time=70):
   - Process 0 (selfIdx=0) is **never evaluated** again because `self=1`.
   - Process 1 (selfIdx=1) is evaluated each cycle but **cannot advance**: its condition `!interested(0) || turn === self` evaluates to `!1 || 0===1 = false || false = false`. Process 1 wrote `turn=0` at cycle 8 (time=80) when it passed through L2, but `self=1` so `turn !== self`.
4. **Both processes are deadlocked**: process 0 is starved by the scheduler (never selected), and process 1 is starved by the turn variable (turn=0, self=1).
5. **Timer counts to 15** and the assertion fires at cycle 19 (time=190).

### Why This Is a Setup Error

The design correctly implements the per-process state machine logic of Peterson's algorithm. However, the **scheduling policy** (which process runs each cycle) is controlled by the unconstrained `io_select` input. For the liveness property `astRelaxedLiveness(pc(0) === Loc.L3, pc(0) === Loc.L4, 15, ...)` to hold, the environment must provide a fair schedule where both processes get to execute within a bounded number of cycles.

The formal solver exploits the lack of fairness constraints by keeping `io_select=1` forever after cycle 6, which:
- Starves process 0 (never gets to execute its state transition)
- Prevents process 0 from ever advancing from L3 to L4
- Causes the timer to exceed its 15-cycle bound

### The Fix

Add fairness assumptions on the `io_select` input to ensure both processes are selected regularly. For example:

```scala
// Constrain select to alternate so both processes make progress
// At minimum, each process must be selected within some bounded window
```

Alternatively, the design could be restructured so both process state machines run independently each cycle (true hardware parallelism), rather than time-multiplexing them onto a single state machine.
